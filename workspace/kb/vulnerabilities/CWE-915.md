# CWE-915: Mass Assignment

## Overview
Mass Assignment (also known as Auto-binding or Overposting) occurs when an application automatically binds request parameters to internal object properties without proper validation, allowing attackers to modify privileged fields.

## Vulnerable Implementations

### 1. Customer Role Assignment
**File**: `packages/api-vulnerable/src/api/v1/customers.routes.ts`

```typescript
// Schema accepts 'role' field
const createCustomerSchema = z.object({
  name: z.string().min(1).max(100),
  phone: z.string().min(10).max(20),
  email: z.string().email().optional(),
  birthDate: z.string().datetime().optional(),
  notes: z.string().max(500).optional(),
  // VULNERÁVEL: Mass Assignment - aceita role
  role: z.string().optional(),
});

// Handler passes role to domain
const { role, ...data } = parseResult.data;
const input = { ...data, userId: req.user!.sub, ... };
if (role) {
  (input as any).role = role; // VULNERÁVEL: Mass assignment de role
}
const customer = await createCustomer.execute(input);
```

### 5. User Role Assignment (CRITICAL)
**File**: `packages/api-vulnerable/src/api/v1/users.routes.ts`

```typescript
const createUserSchema = z.object({
  name: z.string().min(1).max(255),
  email: z.string().email(),
  password: z.string().min(8),
  // VULNERÁVEL: Mass Assignment - aceita role

// Handler passes role directly to domain
const user = createUser({
  name: parseResult.data.name,
  email: parseResult.data.email,

  role: parseResult.data.role as UserRole, // RESPECTS attacker-controlled role!
});
await usersRepo.create(user);
```

## Secure Contrast (api-secure)

### Secure Schema (Excludes Privileged Fields)
```typescript
// packages/api-secure/src/api/v1/customers.routes.ts
const createCustomerSchema = z.object({
  userId: z.string().uuid().optional(),
  name: z.string().min(1).max(255),
  phone: z.string().min(1).max(50).optional(),
  email: z.string().email().optional(),
  birthDate: z.string().datetime().optional(),
  notes: z.string().optional(),
  // NO 'role' field — set by server based on auth context
});
```

### Secure Handler Pattern
```typescript
// Secure: role determined by auth context, not request body
const input = {
  ...parseResult.data,
  userId: req.user!.sub,  // Set from authenticated user
  // role NOT accepted from client
};
const user = createUser({
  name: parseResult.data.name,
  email: parseResult.data.email,
  passwordHash,
  role: parseResult.data.role as UserRole, // Still vulnerable if passed!
});
// FIX: role = req.user?.role === 'ADMIN' ? parseResult.data.role : 'CUSTOMER'
```

## Impact Assessment

| Field | Target | Vulnerable Behavior | Secure Behavior |
|-------|--------|---------------------|-----------------|
| `role` (Customer) | Any user → ADMIN | Ignored by schema/handler |
| `role` (User) | Any user → ADMIN | **NOT in schema** |
| `active` (Barber/Service) | Deactivate any entity | Ignored by schema/handler |

## Impact Assessment

| Impact | Severity |
|--------|----------|
| **Privilege Escalation** | CRITICAL (User role=ADMIN) |
| **Business Logic Bypass** | HIGH (deactivate services/barbers) |
| **Data Integrity** | MEDIUM (unauthorized state changes) |

## Secure Contrast

### api-secure Implementation
- **Schema Validation**: Zod schemas exclude privileged fields (`role`, `active`)
- **Handler Logic**: Privileged fields set server-side based on auth context
- **Domain Enforcement**: Domain entities don't expose setters for privileged fields

```typescript
// api-secure/src/api/v1/users.routes.ts
const createUserSchema = z.object({
  name: z.string().min(1).max(255),
  email: z.string().email(),
  password: z.string().min(8),
  // NO role field
});

const user = createUser({
  name: parseResult.data.name,
  email: parseResult.data.email,
  passwordHash,
  role: 'CUSTOMER', // Always CUSTOMER for self-registration
});
```

## Detection & Remediation

### Detection
- Scan Zod schemas for privileged field names: `role`, `active`, `isAdmin`, `isActive`, `permissions`, `privileges`
- Check handler code for spreading request body directly into domain commands
- Verify domain entities don't expose setters for privileged fields

### Remediation
1. Remove privileged fields from input schemas
2. Set privileged fields server-side based on auth context
3. Make domain entities immutable for privileged fields (no setters)
4. Add integration tests attempting mass assignment → expect 400/ignored
